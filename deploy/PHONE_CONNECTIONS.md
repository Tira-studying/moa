# 휴대폰에서 내 카드·계좌 연결하기

공동관리자와 소유자 모두 서버 터미널 없이 본인 휴대폰의 모아에서 인증할 수 있습니다. 기존 Tailscale HTTPS 주소와 서버 CODEF 설정·별도 저장 키를 사용하며 공개 포트나 새 서버 계정을 만들지 않습니다.

1. Tailscale을 연결하고 **본인의 모아 계정**으로 로그인합니다.
2. **더보기 → 카드·계좌 연결**을 엽니다.
3. 카드 또는 계좌와 기관을 고릅니다. 카드는 삼성·현대·KB국민·신한·롯데·우리, 계좌는 우리은행만 지원합니다.
4. 금융기관 **홈페이지 아이디·비밀번호**와 표시된 본인 확인 항목을 입력합니다. 앱 간편번호·모아 비밀번호와 다릅니다. 전송·암호화 저장 안내에 동의하고 **인증하고 연결하기**를 누릅니다.
5. 문자·이메일 인증번호는 같은 화면에 입력합니다. 앱 인증은 금융기관 앱에서 완료하고 **앱에서 인증을 마쳤어요**를 누릅니다. KB는 하루 첫 조회마다 카드 소지 확인을 다시 요구하므로, KB를 고르면 연결 화면에서 **KB 전체 카드번호와 카드 비밀번호 앞 2자리**를 함께 받습니다. 연결할 때 이 값으로 한 번 조회해 확인된 경우에만 저장하고, 작업자는 KB가 소지 확인(CF-12108)을 요구할 때만 한 번 자동으로 답합니다(새 연결의 첫 조회에서는 KB가 묻지 않을 때가 있어 미리 받습니다). 실패하면 반복하지 않고 다시 인증을 기다립니다. 연결 중에 KB가 따로 소지 확인을 물으면 같은 화면에서 입력하고 **매일 자동 조회에 쓰도록 저장**(기본 켜짐)을 고를 수 있습니다.
6. 카드 지출은 **사용 내역**, 계좌 입출금은 **계좌 입출금**에서 확인합니다. 은행은 **소비로 선택**한 출금만 합산합니다. 이후 한국시간 00·08·14·20시에 수집합니다.

현대는 카드번호·PIN 4자리가 필요하며 동일 RSA 암호문의 재사용과 저장할 암호문을 읽은 조회까지 검증합니다. 우리은행은 본인 원화 계좌번호·PIN 4자리·생년월일 YYYYMMDD 8자리, 롯데는 이름·본인 확인 7자리·휴대폰·통신사를 받습니다. 전체 주민번호는 받지 않습니다. 로그인·기관 통신 오류를 자동 재시도하지 않습니다.

## 보관하는 정보

CODEF가 로그인 정보를 관리하는 연결 ID를 발급합니다. 모아는 홈페이지 로그인 비밀번호·인증번호·롯데 본인 확인 정보를 저장하지 않습니다. KB 소지 정보는 연결 화면에서 입력했거나 추가 인증에서 저장을 고른 경우에만, 소지 확인 조회가 성공한 뒤 카드번호와 RSA 암호화한 비밀번호 앞 2자리를 별도 키로 다시 암호화해 DB에 둡니다(현대와 같은 방식). 전송하거나 화면을 떠나면 입력을 비우며, 브라우저 저장소·PWA 캐시·로그에 인증 입력을 넣지 않습니다.

별도 비밀 볼륨의 기존 키로 연결 정보를 암호화합니다. 현대 웹 연결은 카드번호·CODEF RSA 암호화 PIN을 다시 Fernet으로 감싼 `card_auth_cipher`만 DB에 보관합니다. 기존 비밀 파일도 계속 지원하며 비밀 볼륨을 쓰기 가능으로 바꾸지 않습니다. 우리은행은 기존처럼 연결 ID·계좌번호·생년월일·RSA 암호화 PIN을 다시 암호화해 보관합니다. PIN 평문은 저장하지 않습니다. 이 차이는 기관 선택 시 동의 문구에 표시합니다.

## 중단과 복귀

추가 인증은 현재 로그인 세션에서만 이어갑니다. 새로고침·SMS 앱 복귀 시 진행 상태만 읽으며 로그인을 다시 요청하지 않습니다. 다른 브라우저·새 로그인 세션은 기존 작업을 읽거나 답변할 수 없습니다. 서버 재시작으로 사라진 인증은 만료로 표시하며 자동 재전송하지 않습니다.

작업은 최대 10분, 추가 인증 답변은 최대 170초입니다. **인증 취소** 후에는 이미 전송 중인 응답도 저장하지 않습니다. 로그아웃·계정 접근 해제·연결 변경·본인 자료 버전 변경·서버 키 변경 시에도 새 연결을 저장하지 않습니다. 실패하면 기존 연결·원장·분류·메모를 보존합니다.

같은 기관은 1분 간격, 5분 안에 최대 3회 시도하고 사용자별 동시 인증은 하나입니다. 서버 전체 두 작업 한도와 기존 로컬 CODEF 요청 예산을 적용합니다. 예약 수집과 예산을 공유하므로 동시 요청으로 먼저 소진될 수 있습니다.

## 운영과 검증

현재 표준 Gunicorn 웹 프로세스 **1개**를 전제로 합니다. 인증 세션을 메모리에만 두므로 웹 프로세스를 여러 개로 늘리기 전에는 작업 소유·라우팅을 별도로 설계해야 합니다. `connection_setups`에는 재전송 방지 ID·기관·소유자·세션 해시·시각·결과 상태만 기록하며 인증 원문·연결 ID·추가 인증 세션은 기록하지 않습니다.

가상 기관·임시 DB로 개인 권한, 추가 인증, 취소·로그아웃·버전/키 변경, 중복 요청, 암호화·롤백·휴대폰 배치를 검증합니다. 실제 기관의 인증 정책·차단·통신 오류에는 응답에 따라 중단합니다. 기존 운영자용 CLI도 유지합니다.
